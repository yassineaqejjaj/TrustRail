# Operations runbook

This describes operating TrustRail in whichever environment you deploy it
to. As of this build, only local development has actually been run and
verified — see `docs/BUILD_STATUS.md` for exactly what that means and what
in this document is design/guidance versus tested fact.

## Environment modes

`APP_MODE` (`local` | `demo` | `production`) gates several behaviors:

- Open registration (`POST /v1/auth/register`) — allowed in `local`/`demo`, 403 in `production`.
- Demo endpoints (`POST /v1/demo/*`) — allowed in `local`/`demo`, 403 in `production`.
- Never set `production` without also completing the checklist below.

## Health checks

- `GET /health/live` — process liveness, no dependencies checked.
- `GET /health/ready` — also pings the database; use this for readiness
  probes / load balancer health checks, not `/live`.

## Structured logs and metrics

`apps/api` and `apps/merchant-sandbox` both log structured JSON via `pino`
(disabled in test runs to keep test output readable). Every request gets a
generated `request_id` that also appears in error responses, for
correlating a user-reported failure with server logs.

`GET /v1/metrics/summary` (authenticated, per-organization) reports real
counts and measured authorization-latency percentiles from the
`usage_events` table — see `docs/API.md`. There is no separate
Prometheus/metrics-exporter endpoint in V1; if you need one, scrape this
route per-organization or add a dedicated `/metrics` exporter as a follow-up
(`docs/ROADMAP.md`).

## Database

### Roles

Two Postgres roles, created by `pnpm setup:local` (see
`apps/api/src/db/roles.ts`):

- `trustrail_migrator` — owns the schema, the only role `pnpm migrate` uses.
  Never used by a running server process.
- `trustrail_app` — the runtime role. No `BYPASSRLS`, not the table owner,
  granted only the DML it needs. This is the role every server process
  connects as.

### Migrations

```bash
MIGRATOR_DATABASE_URL=postgres://trustrail_migrator:...@host:port/trustrail \
  pnpm --filter @trustrail/api run migrate
```

Migrations are plain SQL files generated by `drizzle-kit generate` under
`apps/api/migrations/` (and `apps/merchant-sandbox/migrations/` for the
sandbox's own schema) — inspect them before applying in any shared
environment. `pnpm migrate` (the API's migrate script) also (re)applies
`db/rls.sql` and the `trustrail_app` grants every run — both are idempotent.

### Backups

Not automated in V1. For a real deployment: use your Postgres provider's
point-in-time recovery or `pg_dump`/`pg_basebackup` on a schedule, and test
restores regularly (untested backups are not backups).

### Restore

Restoring a backup must not create ambiguity about which actions actually
executed. Concretely: if you restore to a point in time, `execution_jobs`
and `budget_reservations` rows in `reserved`/`unknown` states describe
in-flight state as of that snapshot — do not assume they resolved
favorably. On restore:

1. Do not immediately resume the worker. Reconcile first.
2. For each `unknown` action, query the merchant sandbox's own record by
   the connector idempotency key (the TrustRail action ID) before deciding
   whether to retry, mark failed, or leave pending for manual review.
3. Only then restart the worker (`apps/api/src/worker/poller.ts`, or
   `apps/worker`).

There is no automated tooling for step 2 yet beyond what
`apps/api/src/gateway/dispatch.ts`'s normal retry path already does
(retrying is itself safe, since the connector's own idempotency key
protects against duplication) — a dedicated reconciliation report is listed
in `docs/ROADMAP.md`.

## Signing keys

Generated by `pnpm setup:local` if none exist (`packages/receipt-verifier`
Ed25519 keypair). The private key is written to a local file under
`infra/keys/` (gitignored) and referenced from the `signing_keys` table by
path (`file:...`) — never stored in the database itself. `docs/DECISIONS.md`
notes this as a placeholder for a real KMS integration; the signer
interface (`getActiveSigningKey`/`getTrustedKeys` in
`apps/api/src/gateway/keys.ts`) is already the seam for that swap.

### Rotation

1. Generate a new keypair (reuse `generateSigningKeyPair` from
   `packages/receipt-verifier`, or write a small script following
   `scripts/setup-local.ts`'s pattern).
2. Insert it into `signing_keys` with `status: 'active'`.
3. Update the previous active key's row to `status: 'rotated'` — **never
   delete it**. Historical receipts signed with it must still verify
   (`key_status: 'rotated'`, `signature_valid: true`).
4. If the old key is suspected compromised (not just due for rotation), set
   its status to `revoked` instead of `rotated`. Signature verification
   still succeeds (the math doesn't change); `key_status: 'revoked'` tells
   every verifier not to treat it as currently trustworthy going forward.

## Demo/reset endpoints in production

`APP_MODE=production` returns 403 on every `/v1/demo/*` route
(`assertDemoAllowed` in `apps/api/src/routes/demo.ts`) and on
`/v1/auth/register`. Verify this explicitly before exposing a production
deployment publicly — there is no additional network-level control assumed.

## Deployment checklist (not yet executed end to end)

- [ ] `APP_MODE=production`.
- [ ] `SESSION_COOKIE_SECURE=true` and served over HTTPS.
- [ ] `CORS_ORIGIN` set to the real dashboard origin, not `localhost`.
- [ ] Database roles bootstrapped with strong, unique passwords (not the
      `setup:local` defaults).
- [ ] Signing key private material mounted from a secret store, not a plain
      file on a shared filesystem, if your infra supports it.
- [ ] `infra/docker-compose.yml` reviewed for your target. It has been run
      end-to-end in a local Docker Desktop environment (see
      `docs/BUILD_STATUS.md`'s V15 entry) — a real cloud target still needs
      its own review (TLS termination, secret storage, `APP_MODE=production`,
      the checklist items above), not just a rerun of the local compose file.
- [ ] Backup/restore procedure actually rehearsed once, not just read.
